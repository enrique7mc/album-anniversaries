# Phase 3: Apple Music Integration - Research

**Researched:** 2026-02-04
**Domain:** MusicKit JS v3, Apple Music API, Angular CDN script loading
**Confidence:** MEDIUM

## Summary

This phase implements Apple Music as a second music provider alongside Spotify, enabling users to see album anniversaries from their Apple Music library. The research reveals that MusicKit JS v3 provides a unified JavaScript API for Apple Music integration, but requires careful handling of HTTPS requirements, TypeScript definitions, authentication popup flows, and API response mapping.

MusicKit JS v3 represents a paradigm shift from v1, using a single passthrough API method (`music.api.music()`) instead of endpoint-specific methods. The library must be loaded from Apple's CDN (`https://js-cdn.music.apple.com/musickit/v3/musickit.js`) and configured with a developer token (generated by Firebase Function from Phase 2). User authentication uses a popup-based OAuth-like flow that requires HTTPS even on localhost.

The Apple Music API differs from Spotify in several critical ways: library artists endpoint returns ALL artists alphabetically (no "top artists" equivalent), artwork URLs use template strings with width/height parameters, and album data requires separate catalog queries. Response pagination uses a `next` property rather than manual offset calculation.

**Primary recommendation:** Create AppleMusicService implementing MusicService interface, load MusicKit v3 via dynamic script injection in Angular with `musickitloaded` event listener, use custom TypeScript declarations for v3 (no official @types package exists), and implement robust error handling for popup authentication failures.

### Pattern 1: Dynamic CDN Script Loading with Event Listener
**What:** Load external MusicKit JS library from CDN and initialize after script loads
**When to use:** Third-party libraries hosted only on CDN (not available via npm)
**Example:**
```typescript
// musickit-loader.service.ts
import { Injectable } from '@angular/core';

@Injectable({ providedIn: 'root' })
export class MusicKitLoaderService {
  private loadPromise: Promise<void> | null = null;

  loadMusicKit(): Promise<void> {
    if (this.loadPromise) {
      return this.loadPromise;
    }

    this.loadPromise = new Promise((resolve, reject) => {
      // Check if already loaded
      if (window.MusicKit) {
        resolve();
        return;
      }

      // Listen for musickitloaded event
      document.addEventListener('musickitloaded', () => {
        resolve();
      });

      // Create script element
      const script = document.createElement('script');
      script.src = 'https://js-cdn.music.apple.com/musickit/v3/musickit.js';
      script.async = true;
      script.onerror = () => reject(new Error('Failed to load MusicKit JS'));

      document.body.appendChild(script);
    });

    return this.loadPromise;
  }
}
```

### Pattern 2: MusicKit Configuration and Authorization
**What:** Configure MusicKit instance with developer token and trigger user authorization
**When to use:** After MusicKit script loads, before making any API calls
**Example:**
```typescript
// apple-music.service.ts
import { Injectable } from '@angular/core';

@Injectable({ providedIn: 'root' })
export class AppleMusicService implements MusicService {
  private musicKitInstance: any; // Use 'any' or custom types

  async initialize(developerToken: string): Promise<void> {
    await this.loaderService.loadMusicKit();

    // Configure MusicKit
    this.musicKitInstance = window.MusicKit.configure({
      developerToken: developerToken,
      app: {
        name: 'Album Anniversaries',
        build: '1.0.0'
      }
    });
  }

  async authorize(): Promise<string> {
    // Trigger popup authorization flow
    const musicUserToken = await this.musicKitInstance.authorize();
    return musicUserToken;
  }
}
```

### Pattern 3: Apple Music API Passthrough Method
**What:** Use MusicKit v3's `music.api.music()` passthrough method for all API calls
**When to use:** Fetching library artists, catalog albums, or any Apple Music API endpoint
**Example:**
```typescript
// Fetch library artists (paginated)
const response = await this.musicKitInstance.api.music(
  '/v1/me/library/artists',
  { limit: 50, offset: 0 }
);

// Fetch catalog albums for an artist
const albumsResponse = await this.musicKitInstance.api.music(
  `/v1/catalog/us/artists/${artistId}/albums`,
  { limit: 50 }
);

// Use 'next' property for pagination (don't calculate offset manually)
if (response.next) {
  const nextPage = await this.musicKitInstance.api.music(response.next);
}
```

### Pattern 4: Response Mapping to Shared Models
**What:** Map Apple Music API responses to existing Artist/Album interfaces
**When to use:** Converting Apple Music Resource objects to app's internal models
**Example:**
```typescript
private mapToArtist(resource: any): Artist {
  return {
    id: resource.id,
    href: resource.href,
    name: resource.attributes.name,
    popularity: 0, // Apple Music doesn't provide popularity scores
    images: this.mapArtwork(resource.attributes.artwork),
    external_url: resource.attributes.url || '',
    albums: []
  };
}

private mapArtwork(artwork: any): Image[] {
  if (!artwork) return [];

  // Apple Music artwork uses template URLs with {w}x{h} placeholders
  // Generate multiple sizes to match Spotify's image array format
  return [
    {
      url: artwork.url.replace('{w}', '640').replace('{h}', '640'),
      width: 640,
      height: 640
    },
    {
      url: artwork.url.replace('{w}', '300').replace('{h}', '300'),
      width: 300,
      height: 300
    }
  ];
}

private mapToAlbum(resource: any, artistId: string): Album {
  return {
    id: resource.id,
    artist_id: artistId,
    name: resource.attributes.name,
    release_date: resource.attributes.releaseDate, // YYYY-MM-DD format
    release_date_precision: 'day', // Apple Music always provides day precision
    images: this.mapArtwork(resource.attributes.artwork),
    external_url: resource.attributes.url || ''
  };
}
```

### Anti-Patterns to Avoid
- **Multiple configure() calls:** MusicKit instance is singleton - calling configure() multiple times may cause errors. Configure once in app initialization.
- **Manual offset calculation for pagination:** Always use the `next` property from responses. Manual offsets can result in duplicate results or invalid locations.
- **Assuming popup won't be blocked:** Safari's privacy features and popup blockers can prevent authentication. Call `authorize()` directly in click handler, not in async callback.
- **Storing developer token client-side:** Developer token should be fetched from Firebase Function at runtime, not hardcoded in environment files.

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Apple Music authentication popup | Custom OAuth window | MusicKit.authorize() | Handles popup window, cross-origin messaging, token storage, 6-month expiry |
| Developer token generation | Client-side JWT signing | Firebase Function (Phase 2) | ES256 requires private key - never expose client-side |
| Artwork URL templates | String replace logic | Artwork.url(width:height) method | MusicKit provides instance method, though string replace works |
| API request headers | Manual Authorization headers | music.api.music() passthrough | Automatically adds developer token, user token, handles CORS |
| Script loading | Inline <script> tag in index.html | Dynamic script injection with promise | Enables loading control, error handling, prevents blocking app bootstrap |

**Key insight:** MusicKit JS abstracts most of the Apple Music API complexity. Don't bypass it to use the REST API directly unless absolutely necessary - you'll need to implement authentication popups, CORS handling, and token management yourself.

## Common Pitfalls

### Pitfall 1: HTTPS Required Even for Localhost
**What goes wrong:** MusicKit JS fails to initialize or authenticate on http://localhost
**Why it happens:** Encrypted media playback requires HTTPS, even in development
**How to avoid:** Set up local HTTPS before Phase 3 execution (noted in STATE.md todos)
**Warning signs:**
- "MediaKeySystemAccess EME use is not allowed on unique origins" error
- Authorization popup fails to open
- CORS errors even with correct configuration

**Solution:** Use Angular CLI HTTPS mode or tools like mkcert for local SSL certificates:
```bash
# Option 1: Angular CLI built-in HTTPS
ng serve --ssl

# Option 2: mkcert for trusted certificates
mkcert localhost 127.0.0.1
ng serve --ssl --ssl-key localhost-key.pem --ssl-cert localhost.pem
```

### Pitfall 2: No TypeScript Types for v3
**What goes wrong:** TypeScript errors for window.MusicKit, no autocomplete, "Property 'MusicKit' does not exist on type 'Window'"
**Why it happens:** @types/musickit-js only supports v1, DefinitelyTyped hasn't updated for v3
**How to avoid:** Create custom type declarations in src/typings.d.ts
**Warning signs:**
- Cannot find name 'MusicKit'
- Property 'authorize' does not exist on type 'any'
- No IntelliSense for MusicKit methods

**Solution:** Create minimal type declarations:
```typescript
// src/typings.d.ts
declare global {
  interface Window {
    MusicKit: any; // Use 'any' or create detailed interface
  }
}

// Or create detailed interface (time investment)
interface MusicKitStatic {
  configure(config: MusicKitConfiguration): MusicKitInstance;
  getInstance(): MusicKitInstance;
}

interface MusicKitInstance {
  authorize(): Promise<string>;
  api: {
    music(path: string, params?: any): Promise<any>;
  };
}

declare const MusicKit: MusicKitStatic;
```

### Pitfall 3: Safari Popup Blocker Kills Authentication
**What goes wrong:** authorize() opens popup but Safari immediately blocks it, authentication fails silently
**Why it happens:** Safari blocks popups not triggered by direct user interaction; async operations break the "user gesture" chain
**How to avoid:** Call authorize() directly in button click handler, NOT in async callbacks
**Warning signs:**
- Popup opens briefly then disappears
- User token returns undefined
- No error message, just silent failure

**Solution:**
```typescript
// ❌ BAD: Async callback breaks user gesture chain
async onAppleMusicLogin() {
  const developerToken = await this.getDeveloperToken(); // Async!
  await this.appleMusicService.authorize(); // Popup blocked
}

// ✅ GOOD: Authorize in synchronous click handler
async onAppleMusicLogin() {
  // Pre-fetch developer token before user clicks, or...
  this.appleMusicService.authorize(); // Call immediately, fetch token inside
}
```

### Pitfall 4: Private Browsing Breaks document.referrer
**What goes wrong:** MusicKit authentication fails in Safari Private Browsing mode
**Why it happens:** Safari's Advanced Privacy Protections hide `document.referrer` in cross-site popups, but MusicKit relies on it to verify opener identity
**How to avoid:** Detect private browsing and show clear error message (can't fix, Apple bug fixed in recent WebKit)
**Warning signs:**
- Authentication works in normal Safari but fails in Private Browsing
- Error: "Failed to verify opener"
- User stuck on authorization page

**Solution:** This is a known Apple bug with a WebKit fix merged, but may still affect older iOS/Safari versions. Recommend users disable Private Browsing for authentication:
```typescript
// Detection method (not 100% reliable)
private async isPrivateBrowsing(): Promise<boolean> {
  // Heuristic: Private browsing often restricts localStorage
  try {
    localStorage.setItem('test', 'test');
    localStorage.removeItem('test');
    return false;
  } catch {
    return true; // Likely private browsing
  }
}
```

### Pitfall 5: Language/Locale Breaking Authentication
**What goes wrong:** MusicKit refuses to authorize users with non-English browser language
**Why it happens:** MusicKit has known issues with certain locale configurations
**How to avoid:** Document this limitation, provide workaround instructions in error messaging
**Warning signs:**
- Authentication works in English locale but fails in other languages
- Changing browser language fixes the issue
- No clear error message from MusicKit

**Solution:** Temporary workaround:
```typescript
// Display error message with instructions
if (authError) {
  this.errorMessage =
    'Authentication failed. If using a non-English browser language, ' +
    'try temporarily changing to English (United States) in your browser settings.';
}
```

### Pitfall 6: No "Top Artists" Equivalent in Apple Music API
**What goes wrong:** Expecting Apple Music to have parity with Spotify's "top 50 artists" endpoint
**Why it happens:** Apple Music API only provides `/v1/me/library/artists` (ALL library artists, alphabetical)
**How to avoid:** Accept this UX difference, set clear user expectations about data source
**Warning signs:**
- Looking for "recently played" or "top artists" Apple Music endpoint
- Trying to sort library artists by play count

**Solution:** Use library artists endpoint and document the difference:
```typescript
// Spotify: Top 50 artists by listening frequency
// GET https://api.spotify.com/v1/me/top/artists?limit=50

// Apple Music: ALL library artists (alphabetical)
// GET https://api.music.apple.com/v1/me/library/artists?limit=100
```
**Decision:** Accepted in STATE.md as acceptable UX tradeoff for v1.

### Pitfall 7: Album Data Split Between Library and Catalog
**What goes wrong:** Library artists don't include full album details, need separate catalog queries
**Why it happens:** Apple Music API separates user library (references) from catalog (full metadata)
**How to avoid:** Fetch library artists for list, then query catalog for each artist's albums
**Warning signs:**
- Library artist response missing album details
- Trying to use `include=albums` parameter on library endpoint (doesn't work)

**Solution:**
```typescript
// 1. Fetch library artists (just artist IDs and names)
const libraryArtists = await music.api.music('/v1/me/library/artists');

// 2. For each artist, fetch catalog albums
for (const artist of libraryArtists.data) {
  const albums = await music.api.music(
    `/v1/catalog/us/artists/${artist.id}/albums`,
    { limit: 50 }
  );
}
```

### Pitfall 8: Missing Rate Limits Documentation
**What goes wrong:** Assuming no rate limits exist, then hitting throttling in production
**Why it happens:** Apple Music API documentation doesn't prominently document rate limits (as of early 2026)
**How to avoid:** Implement conservative request pacing, handle HTTP 429 responses
**Warning signs:**
- HTTP 429 "RATE_LIMIT_EXCEEDED" responses
- API calls succeed in development but fail with many artists

**Solution:**
```typescript
// No official rate limits, but be conservative
// Fetch artists in batches with delay between requests
const BATCH_SIZE = 5;
const DELAY_MS = 200; // 200ms delay between batches

for (let i = 0; i < artists.length; i += BATCH_SIZE) {
  const batch = artists.slice(i, i + BATCH_SIZE);
  await Promise.all(batch.map(artist => this.fetchAlbumsForArtist(artist)));

  if (i + BATCH_SIZE < artists.length) {
    await this.delay(DELAY_MS);
  }
}
```

### Pitfall 9: User Token Expiration (6 Months)
**What goes wrong:** User token expires after 6 months, app breaks silently
**Why it happens:** Music User Tokens have 6-month lifetime, can't be refreshed automatically
**How to avoid:** Store token expiry timestamp, detect expired tokens, trigger re-authorization
**Warning signs:**
- API calls return 401 Unauthorized after months of working
- No automatic token refresh mechanism
- User has to re-authenticate frequently

**Solution:**
```typescript
// Store token with expiry timestamp
interface StoredToken {
  token: string;
  expiresAt: number; // Unix timestamp
}

// Check expiry before API calls
private isTokenValid(stored: StoredToken): boolean {
  const now = Date.now();
  const bufferMs = 86400000; // 1 day buffer
  return stored.expiresAt - bufferMs > now;
}

// Set expiry when storing token (6 months from now)
private storeToken(token: string): void {
  const sixMonthsMs = 6 * 30 * 24 * 60 * 60 * 1000;
  const stored: StoredToken = {
    token,
    expiresAt: Date.now() + sixMonthsMs
  };
  sessionStorage.setItem('apple_music_token', JSON.stringify(stored));
}
```

### Pitfall 10: Single Device Token Restriction
**What goes wrong:** User authenticates on desktop, tries to use same token on mobile, API fails
**Why it happens:** Music User Token is device-specific, can't be shared across devices
**How to avoid:** Store tokens in sessionStorage (not localStorage), require separate auth per device
**Warning signs:**
- Token works on one device but not another
- Trying to sync token across devices

**Solution:** Use sessionStorage for device-specific storage:
```typescript
// ✅ GOOD: Device-specific storage
sessionStorage.setItem('apple_music_token', token);

// ❌ BAD: Cross-device storage (violates Apple's terms)
localStorage.setItem('apple_music_token', token);
```

### Pitfall 11: Developer Token from Phase 2 Must Be Fetched at Runtime
**What goes wrong:** Hardcoding developer token in environment.ts, exposing it in client bundle
**Why it happens:** Misunderstanding that developer token is "public" (it should be protected)
**How to avoid:** Fetch developer token from Firebase Function before configuring MusicKit
**Warning signs:**
- Developer token visible in browser DevTools
- Token in version control (environment.prod.ts)

**Solution:**
```typescript
// ✅ GOOD: Fetch from Firebase Function (Phase 2)
private async getDeveloperToken(): Promise<string> {
  const callable = this.functions.httpsCallable('getAppleMusicToken');
  const result = await callable({}).toPromise();
  return result.token;
}

// ❌ BAD: Hardcoded in environment
environment = {
  appleMusic: {
    developerToken: 'eyJhbGc...' // NEVER DO THIS
  }
}
```

### Configure MusicKit and Authorize User
```typescript
// apple-music.service.ts (excerpt)
async initialize(): Promise<void> {
  // 1. Load MusicKit script
  await this.musicKitLoader.loadMusicKit();

  // 2. Fetch developer token from Firebase Function
  const developerToken = await this.getDeveloperToken();

  // 3. Configure MusicKit instance (singleton)
  this.musicKitInstance = window.MusicKit.configure({
    developerToken: developerToken,
    app: {
      name: 'Album Anniversaries',
      build: '1.0.0'
    }
  });
}

async authorize(): Promise<string> {
  if (!this.musicKitInstance) {
    throw new Error('MusicKit not initialized');
  }

  try {
    // Trigger popup authorization (must be in click handler)
    const musicUserToken = await this.musicKitInstance.authorize();

    // Store with 6-month expiry
    this.storeToken(musicUserToken);

    return musicUserToken;
  } catch (error) {
    console.error('[AppleMusicService] Authorization failed:', error);
    throw error;
  }
}

private async getDeveloperToken(): Promise<string> {
  const callable = this.functions.httpsCallable('getAppleMusicToken');
  const result = await callable({}).toPromise();
  return result.token;
}
```

### Fetch Library Artists with Pagination
```typescript
// apple-music.service.ts (excerpt)
private async fetchAllLibraryArtists(): Promise<any[]> {
  let artists: any[] = [];
  let nextUrl: string | null = '/v1/me/library/artists';

  while (nextUrl) {
    const response = await this.musicKitInstance.api.music(nextUrl, {

    });

    artists = artists.concat(response.data);

    // Use 'next' property for pagination (don't calculate offset)

  }

  return artists;
```

### Map Apple Music Responses to Shared Models
```typescript
// apple-music.service.ts (excerpt)
private mapToArtist(resource: any): Artist {
  return {
    id: resource.id,
    href: resource.href,
    name: resource.attributes?.name || 'Unknown Artist',
    popularity: 0, // Apple Music doesn't provide popularity
    images: this.mapArtwork(resource.attributes?.artwork),
    external_url: resource.attributes?.url || '',
    albums: []
  };
}

private mapArtwork(artwork: any): Image[] {
  if (!artwork || !artwork.url) {
    return [];
  }

  // Apple Music artwork uses template: {w}x{h}bb.jpg
  // Generate multiple sizes to match Spotify format
  const sizes = [
    { width: 640, height: 640 },
    { width: 300, height: 300 },
    { width: 64, height: 64 }
  ];

  return sizes.map(size => ({
    url: artwork.url
      .replace('{w}', size.width.toString())
      .replace('{h}', size.height.toString()),
    width: size.width,
    height: size.height
  }));
}

private mapToAlbum(resource: any, artistId: string): Album {
  return {
    id: resource.id,
    artist_id: artistId,
    name: resource.attributes?.name || 'Unknown Album',
    release_date: resource.attributes?.releaseDate || '', // YYYY-MM-DD
    release_date_precision: 'day', // Apple Music always day precision
    images: this.mapArtwork(resource.attributes?.artwork),
    external_url: resource.attributes?.url || ''
  };
}
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| MusicKit JS v1 with endpoint-specific methods | MusicKit JS v3 with passthrough `api.music()` method | v3 beta (2023+) | Simpler API, single method for all endpoints, better TypeScript compatibility (if types existed) |
| Implicit Grant OAuth (deprecated) | MusicKit popup authorization | 2019+ | More secure, handles cross-origin messaging, manages token storage |
| HTTP allowed for localhost | HTTPS required everywhere | Recent (2020s) | Better security, but adds development setup complexity |
| Developer token in client bundle | Developer token from backend endpoint | Best practice 2020+ | More secure, enables token rotation without redeployment |

**Deprecated/outdated:**
- **MusicKit v1 methods**: `music.api.library.artists()`, `music.api.catalog.albums()` - replaced by `music.api.music('/v1/...')` passthrough in v3
- **Manual offset pagination**: Calculating offsets manually - replaced by using `next` property from responses
- **HTTP development servers**: http://localhost - replaced by https://localhost requirement

## Open Questions

Things that couldn't be fully resolved:

1. **MusicKit v3 TypeScript Types**
   - What we know: No official @types package exists for v3, only v1 types available
   - What's unclear: Will Apple provide official types, or should we create comprehensive custom declarations?
   - Recommendation: Start with minimal `any` types, refine as needed. Creating full type definitions is time-consuming and may become outdated when Apple releases official types.

2. **Mobile Safari Authentication Fallback**
   - What we know: Safari popup blockers and Private Browsing can break authentication
   - What's unclear: What fallback strategies work reliably on iOS? Redirect-based flow possible?
   - Recommendation: Defer to Phase 4 (Production Validation) - implement basic popup flow first, add fallbacks if real device testing reveals issues.

3. **Apple Music API Rate Limits**
   - What we know: No formal rate limits documented as of early 2026, but other Apple APIs have limits
   - What's unclear: Actual throttling behavior, whether limits apply per-user or per-app
   - Recommendation: Implement conservative request pacing (5 concurrent requests, 200ms delay between batches), handle HTTP 429 gracefully.

4. **Storefront Detection**
   - What we know: Catalog queries require storefront code (e.g., 'us', 'gb')
   - What's unclear: Best method to detect user's storefront? Does MusicKit provide this automatically?
   - Recommendation: Start with hardcoded 'us', investigate MusicKit.getStorefront() or IP-based detection if users report missing albums.

5. **Developer Token Caching Strategy**
   - What we know: Phase 2 implements 180-day caching with 1-hour refresh buffer in Firebase Function
   - What's unclear: Should client cache token for session duration, or fetch fresh on each page load?
   - Recommendation: Cache developer token in memory for session lifetime, fetch fresh on app initialization. Don't persist to storage (changes require redeployment anyway).
